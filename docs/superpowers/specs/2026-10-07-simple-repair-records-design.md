# บันทึกการซ่อมแบบฟอร์มเดียว — Design

> วันที่: 2026-10-07 · branch: `feat/simple-repair-records` (ต่อจาก `fix/security-round-1`)
> สถานะ: ผู้ใช้อนุมัติการออกแบบทั้ง 5 ส่วนในแชตแล้ว · รอตรวจไฟล์ spec

## 1. เป้าหมายและหลักฐาน

**ผู้ใช้ต้องการ:** งานซ่อมเป็นแค่ "บันทึกการซ่อม" — ขั้นตอนเยอะพนักงานจะไม่ทำ

**หลักฐานจากข้อมูลจริง** (`asset_management_dev` คัดลอกจาก Production 2026-10-07):

- ใบซ่อมทั้งหมดตั้งแต่ มิ.ย. 2026 มี 4 ใบ (ปิดแล้วทั้งหมด) · แผน PM 0 แผน · ไฟล์แนบงานซ่อม 6 ไฟล์
- ทรัพย์สิน 10 ชิ้นค้างสถานะ "รอซ่อม" (8) / "อยู่ระหว่างซ่อม" (2) โดยไม่มีใบซ่อม — พนักงานข้ามขั้นตอน ประวัติซ่อมหาย

**สำเร็จเมื่อ:** พนักงานบันทึกการซ่อมจริงด้วยฟอร์มเดียว · ทุกชิ้นมีประวัติซ่อม (เมื่อไหร่ อาการ/สิ่งที่ซ่อม ผล ค่าใช้จ่าย ใครซ่อม) · ไม่มีทรัพย์สินค้างสถานะซ่อมโดยไม่มีบันทึกที่ยังไม่เสร็จ

**นอกขอบเขต:** การอนุมัติค่าซ่อม · การมอบหมายงาน · SLA · ระบบช่าง/ใบสั่งงาน

## 2. แนวทางที่เลือก

ใช้ตาราง `maintenance_tickets` และ `maintenance_plans` เดิม (ผู้ใช้เลือกแนวทาง A) · ไม่ลบคอลัมน์หรือตาราง · ประวัติ 4 ใบเดิมแสดงต่อได้ · เพิ่มคอลัมน์ `outcome` หนึ่งคอลัมน์

แนวทางที่ไม่เลือก: ตารางใหม่ (ต้องย้ายข้อมูลและแก้รายงานทุกจุด) · ปุ่มบันทึกด่วนบน workflow เดิม (ความซับซ้อนยังอยู่ในโค้ดและหน้าจอ)

## 3. สถานะและกฎ

### 3.1 สถานะของบันทึก (`repairStatus`)

| ค่า | ความหมาย |
|---|---|
| `in_progress` | ยังซ่อมไม่เสร็จ (ส่งซ่อม / รออะไหล่) |
| `closed` | เสร็จแล้ว — มี `outcome` |
| `cancelled` | ยกเลิก (บันทึกผิด) — เก็บประวัติ |

ข้อมูลเดิมที่เป็น `open`, `reported`, `accepted`, `waiting_parts`, `waiting_vendor`, `completed` ถือเป็น "ยังซ่อมไม่เสร็จ" ทุกจุด (อ่านอย่างเดียว ไม่เขียนค่าเหล่านี้ใหม่)

### 3.2 ผลการซ่อม (`outcome`, คอลัมน์ใหม่ `NVARCHAR(20) NULL`)

`usable` (ใช้งานได้ — ค่าเริ่มต้น) · `beyond_repair` (ซ่อมไม่ได้ เสนอจำหน่าย) · `NULL` = ข้อมูลเดิม "ไม่ระบุ"

### 3.3 ผลต่อสถานะทรัพย์สิน

"สถานะตามผู้ถือครอง" = `In Use` ถ้ามี checkout ที่ยัง active (ส่งมอบถาวร) หรือเป็นของส่วนตัวที่มีผู้ถือครอง (`getMaintenanceOperationalTarget` เดิม) มิฉะนั้น `Ready` — ข้อแรกเพิ่มตอนเขียนแผน เพื่อให้ของที่ส่งมอบถาวรยังคืนได้หลังซ่อม

| การกระทำ | เงื่อนไข | สถานะทรัพย์สินหลังบันทึก |
|---|---|---|
| บันทึก "เสร็จแล้ว / ใช้งานได้" | ทรัพย์สินไม่ใช่ Disposed/Retired · ไม่มีบันทึกที่ยังไม่เสร็จอยู่ (ถ้ามีให้กด "ซ่อมเสร็จ" ที่บันทึกนั้นแทน) | ไม่เปลี่ยน · ยกเว้นทรัพย์สินที่ค้าง `Pending Repair`/`Under Maintenance` → สถานะตามผู้ถือครอง |
| บันทึก "เสร็จแล้ว / ซ่อมไม่ได้" | เหมือนข้างบน + ไม่มี checkout ที่ยัง active | `Pending Disposal` |
| บันทึก "ยังซ่อมไม่เสร็จ" | สถานะ `Ready` / `In Use` / `Pending Repair` (ข้อมูลเดิม) · ไม่มีบันทึกที่ยังไม่เสร็จ · `Checked Out` ต้องคืนก่อน | `Under Maintenance` |
| กด "ซ่อมเสร็จ" (ใช้งานได้) | บันทึกยังไม่เสร็จ | สถานะตามผู้ถือครอง |
| กด "ซ่อมเสร็จ" (ซ่อมไม่ได้) | บันทึกยังไม่เสร็จ · ไม่มี checkout ที่ยัง active | `Pending Disposal` |
| ยกเลิกบันทึกยังไม่เสร็จ | — | สถานะตามผู้ถือครอง |
| ยกเลิกบันทึกที่เสร็จแล้ว | ไม่อนุญาต (แก้ไขแทน) | — |

ทุกการเปลี่ยนสถานะทรัพย์สินใช้ conditional update บน `statusId` ใน transaction (แบบ round 2) และเขียน `asset_movements` + System Log

`Pending Repair` เลิกใช้กับงานใหม่ (คงไว้ใน master data เพื่ออ่านประวัติ)

### 3.5 การแก้ไขบันทึก

- `maintenance:edit` แก้ได้เฉพาะรายละเอียด: วันที่ · อาการ/สิ่งที่ซ่อม · ร้าน · ค่าใช้จ่าย · เลขใบเสร็จ · หมายเหตุ · ไฟล์แนบ (เพิ่ม/ลบ)
- สถานะและผลการซ่อมเปลี่ยนผ่าน "ซ่อมเสร็จ" / "ยกเลิกบันทึก" เท่านั้น · บันทึกที่เสร็จแล้วเปลี่ยนผลไม่ได้ · ถ้าผลผิดจนสถานะทรัพย์สินผิด ให้แก้สถานะด้วย Status Correction เดิม (มีเหตุผลและ log) แล้วระบุในหมายเหตุของบันทึก
- ทุกการแก้ไขใช้ optimistic concurrency (`expectedUpdatedAt`) และเขียน System Log

### 3.4 แผน PM

- เก็บ: ทรัพย์สิน · ชื่องาน · รอบ (`frequency`/`intervalDays`) · `nextDueDate` · ร้านประจำ · หมายเหตุ · `planState` (active/paused/ended)
- เลิกใช้: `assignedToId`, `lastGeneratedAt`, การสร้างใบงานอัตโนมัติ
- "PM ถึงกำหนด" = แผน `active` ที่ `nextDueDate` ≤ วันนี้ + 7 วัน (เวลาไทย) และทรัพย์สินไม่ใช่ Disposed/Retired · เรียงที่เลยกำหนดก่อน
- "บันทึกว่าทำแล้ว" เปิดฟอร์มเดียวกัน กรอก ทรัพย์สิน, อาการ = ชื่องาน, ร้าน, "เสร็จแล้ว / ใช้งานได้" ไว้ให้ · บันทึกพร้อม `maintenancePlanId`
- เมื่อบันทึกที่ผูกแผนถูกสร้าง: `nextDueDate` = วันที่ในบันทึก + รอบ (รายเดือน/รายไตรมาสใช้การบวกเดือนแบบ clamp วันสิ้นเดือน)
- เมื่อทรัพย์สินถูก execute จำหน่ายเป็น Disposed/Retired: แผนของทรัพย์สินนั้นเปลี่ยนเป็น `ended`

## 4. หน้าจอ

### 4.1 ฟอร์ม "บันทึกซ่อม"

| ช่อง | บังคับ | หมายเหตุ |
|---|---|---|
| ทรัพย์สิน | ✔ | เติมให้เมื่อมาจากหน้าทรัพย์สิน/สแกน/PM |
| วันที่ | ✔ | ค่าเริ่มต้นวันนี้ตามเวลาไทย (`toLocalDateInputValue`) |
| อาการ / สิ่งที่ซ่อม | ✔ | ช่องข้อความเดียว (`problem`) |
| สถานะ | ✔ | ● ซ่อมเสร็จแล้ว ○ ยังซ่อมไม่เสร็จ |
| ผลการซ่อม | เมื่อเสร็จ | ● ใช้งานได้ ○ ซ่อมไม่ได้ เสนอจำหน่าย |
| รายละเอียดเพิ่มเติม (พับเก็บ) | ✘ | ผู้ซ่อม: ช่างภายใน / ร้าน (`vendorId`) · ค่าใช้จ่ายรวม (`repairCost`) · เลขใบเสร็จ (`invoiceNo`) · แนบรูป/ใบเสร็จ · หมายเหตุ (`resolution`) |
| ผู้บันทึก | อัตโนมัติ | พนักงานที่ผูกกับบัญชี · ถ้าบัญชีไม่ผูกพนักงาน แสดงช่องเลือก (บังคับ) |

ช่องเดิมที่ไม่ใช้ในฟอร์มใหม่: `assignedToId`, `dueDate`, `laborCost`, `partsCost`, `quotationNo`, `warrantyClaim`, `rootCause`, `inspectedById` (คงคอลัมน์ ข้อมูลเดิมแสดงในหน้ารายละเอียดถ้ามีค่า)

`repairType`: `vendor` เมื่อเลือกร้าน มิฉะนั้น `internal` (ค่าเดิมในระบบ) · `reportedDate` = วันที่ในฟอร์ม · `returnDate` = วันที่ซ่อมเสร็จ

### 4.2 จุดที่บันทึกได้

- **หน้าทรัพย์สิน**: ปุ่ม "บันทึกซ่อม" แทน "แจ้งซ่อม" + ประวัติซ่อมของชิ้นนั้น
- **หน้าซ่อมบำรุง**: รายการบันทึก (ตัวกรอง ยังไม่เสร็จ / เสร็จ / ยกเลิก / ช่วงวันที่ / คำค้น) · ปุ่ม "บันทึกซ่อม" · กล่อง "PM ถึงกำหนด" · กล่อง "ทรัพย์สินค้างสถานะซ่อมแต่ไม่มีบันทึก" พร้อมปุ่มบันทึก
- **คืนของ (check-in)**: ผลการคืน "ส่งซ่อม" แทน "รอซ่อม + ติ๊กสร้างใบซ่อม" → บันทึก `in_progress` จากหมายเหตุความเสียหาย และทรัพย์สินเป็น `Under Maintenance`
- **บันทึกที่ยังไม่เสร็จ**: ปุ่มเดียว "ซ่อมเสร็จ" เปิด dialog: วันที่รับคืน (บังคับ) · ผลการซ่อม · ค่าใช้จ่าย/แนบไฟล์ (ไม่บังคับ) · และปุ่ม "ยกเลิกบันทึก" (ยืนยันด้วย dialog)
- **มือถือ**: สแกน QR → หน้าทรัพย์สิน → "บันทึกซ่อม" · touch target ≥ 44px

### 4.3 สิ่งที่เอาออก

สถานะ reported/accepted/in_progress เดิม/waiting/completed และปุ่มเปลี่ยนสถานะ · มุมมองกระดาน · การมอบหมายและแก้ planning · วันครบกำหนด/SLA และแจ้งเตือนซ่อมเกินกำหนด · เช็กลิสต์ปิดงานและการบังคับหลักฐาน · รายการอนุมัติปิดงานซ่อมในกล่องอนุมัติ และค่าตั้ง `workflow_approval_maintenance_close_required` · job `pm:generate-due` / ส่วน PM ใน `scheduler:heartbeat` และค่าตั้ง `pm_auto_generation_*`

## 5. ผลกระทบกับโมดูลอื่น

| ที่ | การเปลี่ยน |
|---|---|
| Dashboard | KPI "อยู่ระหว่างซ่อม" นับจากบันทึกที่ยังไม่เสร็จ · การ์ด "ซ่อมเกินกำหนด" → "ยังซ่อมไม่เสร็จ" |
| ศูนย์งานค้าง | เหลือการ์ด "ยังซ่อมไม่เสร็จ" และ "PM ถึงกำหนด" |
| แจ้งเตือน / digest | เลิกแจ้งซ่อมเกินกำหนด · เพิ่ม "PM ถึงกำหนด" |
| กล่องอนุมัติ / approval matrix | ไม่มีชนิดปิดงานซ่อม |
| Asset State Review | กฎ: ทรัพย์สิน `Pending Repair`/`Under Maintenance` ที่ไม่มีบันทึกยังไม่เสร็จ |
| การจำหน่าย (readiness `active_maintenance`) | นับบันทึกที่ยังไม่เสร็จ (ค่าเดิมทั้งหมดที่ไม่ใช่ closed/cancelled) |
| legacy checkout | ตรวจบันทึกที่ยังไม่เสร็จ (ไม่ใช้ prefix `[PM] ` อีก) |
| หน้าพนักงาน / ผู้ขาย | ประวัติซ่อมที่บันทึก / ที่ร้านนั้นซ่อม |
| ค้นหา · export Excel · หน้าพิมพ์ | ใช้ชุดช่องใหม่ (วันที่ · ทรัพย์สิน · อาการ/สิ่งที่ซ่อม · สถานะ · ผล · ร้าน · ค่าใช้จ่าย · ผู้บันทึก) |
| สิทธิ์ | `maintenance:create` บันทึก · `maintenance:edit` ซ่อมเสร็จ/แก้ไข/ยกเลิก · `maintenance:view` ดู (ของเดิม) |

การแยกว่าบันทึกไหนมาจากแผน PM ใช้ `maintenancePlanId` เท่านั้น ไม่ใช้ข้อความ `[PM] ` ขึ้นต้นอีก (แก้ B5)

## 6. ข้อผิดพลาดที่ผู้ใช้เห็น (ภาษาไทย)

| กรณี | ข้อความ |
|---|---|
| ทรัพย์สินถูกยืมอยู่ และเลือก "ยังไม่เสร็จ" หรือ "ซ่อมไม่ได้" | ทรัพย์สินนี้ถูกยืมอยู่ กรุณาบันทึกคืนก่อน |
| มีบันทึกที่ยังไม่เสร็จอยู่แล้ว | ทรัพย์สินนี้มีงานซ่อมที่ยังไม่เสร็จ กด "ซ่อมเสร็จ" ที่บันทึกนั้นแทน (มีลิงก์) |
| ทรัพย์สินจำหน่าย/ปลดระวางแล้ว | ทรัพย์สินนี้ออกจากทะเบียนแล้ว บันทึกซ่อมไม่ได้ |
| ข้อมูลเปลี่ยนระหว่างบันทึก (conflict) | ข้อมูลทรัพย์สินเพิ่งถูกเปลี่ยน กรุณาโหลดใหม่แล้วลองอีกครั้ง |

API ส่ง `code` คงที่ (เช่น `MAINTENANCE_ASSET_ON_LOAN`) · หน้าจอแปลด้วย messages th/en
