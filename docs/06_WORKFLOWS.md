# Workflows

## Asset State Review Queue

- Open `Admin > Data Quality` and use **Asset state review queue / รายการรอตรวจสอบสถานะและสภาพทรัพย์สิน**.
- Users with `setting:view` can filter pending, resolved, and dismissed findings by severity and issue type. Users with `setting:edit` can scan current data and act on pending findings.
- Scan is review-first: it creates or refreshes `asset_state_reviews` and never updates `assets.statusId` or `assets.conditionId` automatically.
- Use **Resolve** only for the issue-specific active status or selectable condition offered by the server. The system rejects stale snapshots and asks the operator to scan again.
- Use **Dismiss** only after confirming the current data is correct. Both actions require an auditable reason of at least 10 characters.
- Issues representing a real transaction should be completed through checkout/check-in, transfer, maintenance, disposal, or audit workflow rather than by inventing a direct status change.

## Asset Registration

- Add a single asset from `/assets/new`.
- Clone an existing asset from Asset Register or Asset Detail when adding another similar asset. The clone flow opens `/assets/new?cloneFrom={assetId}`, copies shared master, ownership, location, purchase, warranty, custom-field, and linked purchase-document data (the active documents only, as chips; none for a user without `asset:edit`), but leaves Asset Tag, Serial Number, and FA/accounting code blank for the new record.
- Add a batch of assets from the same page using shared purchase/master data plus row-level serial/manual asset tag data by default. When a batch contains assets spread across holders, departments, or sites, open the optional row columns for custodian, department, current location, home location, and remark; blank row fields fall back to the shared batch values.
- Single and batch create auto-select the model when the selected category and brand uniquely match one active model; users can still choose a specific model when more than one exists.
- Import legacy assets from Excel on `/asset-management/import-export` (`asset:create`; page group 4 plan 5, spec §13). The import card is open on arrival: five steps (แม่แบบ, อัปโหลด, ตรวจสอบ, นำเข้า, เสร็จสิ้น), "ดาวน์โหลดแม่แบบ" (its Statuses and Conditions sheets list only the values an import may use), then a dropzone for one `.xlsx` of at most 10 MB and 1,000 data rows. Headers may be the template's English names or the Thai field names. The preview (`POST /api/assets/import-preview`) checks every row and writes nothing; each problem reads "<ชื่อช่อง>: <ปัญหา>" with "ค่าในไฟล์: <value>" under it, and " · ใช้อยู่กับ <tag>" (a link; "ที่ปิดใช้งานแล้ว" for an inactive asset) when a tag or Serial is already in the register, or "ซ้ำกับแถว n ในไฟล์". Only Draft or Ready statuses import; a year from 2400 to 2700 is refused as พ.ศ.; text dates are yyyy-m-d or d/m/yyyy; an Excel error value (#N/A, #REF! …) is refused. The rows filter by มีข้อผิดพลาด / พร้อมนำเข้า / ทั้งหมด (errors first when there are any; at most 100 rows shown). The person fixes the file and drops it again ("อัปโหลดไฟล์ที่แก้แล้ว"), or presses "ยืนยันนำเข้า N รายการ", which imports exactly the N ready rows and skips the others: confirm checks the file again and refuses with 409 when the ready count changed (the page shows the new result), the batch was already used, or the register changed during the write; the batch is one transaction, so a refusal imports nothing. A blank tag is generated; a held บุคคล or Stock row takes its holder's department (the create rule). The done state shows "นำเข้าแล้ว n รายการ · ข้าม n แถว", links to the first 5 assets, "นำเข้าไฟล์ใหม่" and "ดูในทะเบียนทรัพย์สิน". The page's ประวัติรอบนำเข้า lists the last 10 batches by file name with นำเข้าครบ / นำเข้าบางส่วน and the skipped rows with their problems (up to 50 kept per batch). A viewer sees the export card and the history only.
- Export from the same page: "ส่งออกทั้งหมด (Excel)" writes every active asset with the count "N รายการ · ไม่ใช้ตัวกรอง" (above 5,000 the file holds the 5,000 added last, and the line says so); "ส่งออกตามตัวกรองในทะเบียน" (from `md`) goes to the register, whose "ส่งออก / นำเข้า" menu exports the filtered list.
- Asset tags may be manually entered for legacy assets or auto-generated when left blank.
- Use the Asset Register quick filters for common operational queues such as missing Serial, missing photo, purchase-info gaps, warranty expiring, missing responsibility, Ready, In Use, Checked Out, Pending Repair, and Under Maintenance. Quick filters are grouped by data quality, ownership/custody scope, and lifecycle status, update the URL, and preserve the current search/company/branch/category context. On mobile the groups scroll horizontally so the first asset cards are not pushed far below the fold.
- Asset Register accepts drilldowns from master data counts: category asset counts open the register with `categoryId`, brand asset counts open it with `brandId`, and model asset counts open it with `modelId`. Active Brand/Model drilldowns appear as removable chips above the register filters and stay preserved when applying additional filters.
- The Asset Register filter panel keeps the daily filters visible first: search, company, branch, and category are the primary controls. Status, condition, ownership type, and rows-per-page live in a collapsible advanced section that opens automatically when one of those filters is active. Status and condition stay grouped with compact help icons.
- The Asset Register search box ("ค้นหา รหัส · ชื่อ · Serial · ผู้ถือครอง · ที่ตั้ง") can find assets by Asset Tag, name, Serial, Fixed Asset Code, master-data codes, custodian name, and the current custodian's employee code, and by the current location's code or name. It intentionally searches only the current holder's `Employee.code`, not repair reporters, repair assignees, or other employees related through history. Typing a person's name lists the assets they hold now (page group 4 plan 1).
- The register rows (page group 4 plan 1, spec `docs/superpowers/specs/2026-11-01-page-group-4-register-form-design.md` §6): on the desktop one ทรัพย์สิน column holds the photo, the full name (up to two lines) and the tag under it; ที่ตั้ง shows the room with its branch under it; ผู้ถือครอง shows the holder with their department under the name (or "ส่วนกลาง · ไม่มีผู้ถือครอง" / "ไม่มีผู้ถือครอง"), and "คืน <date>" for a temporary loan; the condition is plain text, a badge only when it needs a look. On the phone the card leads with the name as its link, then the tag with the status, then "<holder> · <room>"; above the cards "<tab> N รายการ", and on the last page "แสดงครบ N จาก N รายการ".
- The status tabs are ทั้งหมด, the five lifecycle tabs and **สถานะอื่น** (`statusGroup=other`: every status that has no tab of its own, such as รอตัดจำหน่าย). The line under the tabs adds them up to ทั้งหมด and names the three largest other statuses. A dashboard link to one status with no tab (`?statusId=…&exact=1`) makes สถานะอื่น the current tab, with the status's chip.
- The header holds "ส่งออก / นำเข้า" (desktop): "ส่งออกตามตัวกรอง (N รายการ)", and for `asset:create` the import template and "นำเข้าจาก Excel", which opens `/asset-management/import-export`. The import card lives on that page only; the register no longer shows it. The page sizes (10, 25, 50, 100) sit in the footer beside the pager. The table defaults to the Operations column preset before stored browser preferences load, then remembers All, Operations, Accounting, and Audit views in that browser; the column picker reads "ชุดคอลัมน์: <preset>", and a list stored before page group 4 that named the old รหัส and ชื่อ columns opens with the one ทรัพย์สิน column. Column/export/template utility buttons are desktop-only; mobile users work from the compact asset cards.
- Saved views (page group 4 plan 1, §6.4): on the desktop, "มุมมองที่บันทึกไว้:" under the toolbar lists the views this person kept in this browser (localStorage per user and language, at most 12, names up to 40 characters); "+ บันทึกมุมมองนี้" keeps the current filters, tab, sort and page size under a name, each view's ⋯ renames or deletes it, and the view on screen is marked. On the phone a button beside the filter button opens the kept views; saving is desktop only. A view is not shared with anyone and does not follow the person to another browser.
- Ticking rows opens the selection bar: on the desktop the shared sticky bar with "N รายการที่เลือกในหน้านี้", "ล้างรายการที่เลือก", "อื่น ๆ" (อัปเดตที่ตั้ง/ผู้ถือครอง for `asset:edit`, ส่งออกรายการที่เลือก) and "พิมพ์ป้าย N รายการ"; on the phone the floating bar above the bottom navigation.
- The register's bulk update ("แก้ไขข้อมูลหลายรายการ", page group 4 plan 1, decision 11) is a correction of the record, not a move: it sets a room, a holder or both on up to 100 ticked assets with "เหตุผลที่แก้". It follows the department rule (`getTransferNextDepartmentId`): a บุคคล or Stock asset takes the holder's department (the dialog says "แผนกจะเปลี่ยนตามผู้ถือครอง: <แผนก> (N รายการ)"), a ส่วนกลาง or ส่วนควบ asset keeps its own; a room-only correction of a held บุคคล asset brings its department to the holder's. A holder given to a บุคคล or Stock asset makes it In Use. It refuses what ย้ายที่ตั้งหลายรายการ refuses (an asset no longer active, an outstanding ส่วนควบ, License, an open handover, a status that cannot take the change) in one answer naming every refused asset, listed under the form with "นำรายการเหล่านี้ออกจากที่เลือก"; it does not refuse a broken condition. The history reads "แก้ไขข้อมูลที่ตั้ง", "แก้ไขข้อมูลผู้ถือครอง" and "แก้ไขข้อมูลแผนก" with the reason, counted under the chip แก้ไขข้อมูล; installed components follow the parent's change.
- The edit page (page group 4 plan 2, spec §7, decisions 5, 6 and 10) corrects what was recorded wrong; it is not a move. A real move of the machine or a new user goes through โอนย้าย (or ส่งมอบ / รับคืน), which writes a TR- (or HO- / RT-) and the history of a move; the hint under ที่ตั้งปัจจุบัน and the holder links to โอนย้าย with the asset. The page:
  - shows "แก้ไข <name>" with the tag, the status, the holder with their department, the room with its branch and "ดูหน้าทรัพย์สิน"; the first card "ข้อมูลที่ต้องกรอก" (as on create, no counter), then the folded sections, the last one หมายเหตุ;
  - marks every changed field "แก้แล้ว" with "เดิม: <value>" and "คืนค่าเดิม", and lists them in the footer's "แก้ไข n ช่อง" (a popover on the desktop, a bottom sheet on the phone) with "ไปที่ช่อง"; the save is "บันทึกการแก้ไข";
  - asks for "เหตุผลที่แก้" (required, up to 500 characters) when the person changes the room, the holder or แผนก. `PUT /api/assets/[id]` takes it as `correctionReason`; without it the save is refused under the field (400 `fieldErrors.correctionReason`), after the open-handover lock (409).
- The department rule on the asset form (P2-R1, `getRegisterDepartment` in `src/lib/asset-department-rule.ts`, the same helper for create, edit and the form's lock): a บุคคล or Stock asset with a holder takes the holder's department, shown as "ตามผู้ถือครอง: <แผนก>" and not pickable; with no holder, and for ส่วนกลาง, ส่วนควบ and License, แผนก is free. A cleared holder frees it. A save of a held บุคคล or Stock asset whose stored department is not its holder's, with the holder unchanged, writes the holder's department as an automatic fix: the change list marks it "ปรับตามผู้ถือครอง" and no reason is asked. The fix is skipped (the department the save sends stays) while a handover is open and on a written-off asset (Disposed, Retired: `move_scope` refused), whose custody cannot move; there the custody lock refuses only a department changed by hand. The server applies the rule whatever the client sends; a new holder who is no longer active is refused under the holder (409 `ASSET_TRANSFER_DESTINATION_INACTIVE`).
- The holder on the asset form shows for every type that can have one (บุคคล, ส่วนกลาง, Stock, and License as its assignee) and lists the active employees of the owner company and branch, with no department filter; a change of ownership type keeps the holder, except a change to ส่วนควบ (a component takes its parent's holder through the sync). The `isActive` checkbox left the form: `PUT` ignores `isActive`, and `POST` always creates an active asset; deactivation stays on the delete action.
- The edit history (P2-R5): one save shares one `referenceId` (`referenceType: "register_edit"`). The room, the holder and แผนก write `register_location_correction`, `register_custodian_correction` and `register_department_correction` ("แก้ไขข้อมูลที่ตั้ง", "แก้ไขข้อมูลผู้ถือครอง", "แก้ไขข้อมูลแผนก") with the reason (the automatic fix with none); the edit no longer writes `location_change`, `custodian_change` or `department_change`, which stay for the transactions. Each of 14 fields (name, Serial, category, brand, model, company, branch, ownership type, purchase date and price, warranty start and end, PO and invoice numbers) writes one `register_field_correction` ("แก้ไขข้อมูลทรัพย์สิน") from → to; `ownership_type_change` is no longer written. Status, condition and the License fields keep their own types. The dashboard's recent feed leaves field corrections out. `register_field_correction` and `asset_tag_change` are not activity (`ASSET_MOVEMENT_NOT_ACTIVITY_TYPES` in `src/lib/asset-movement-labels.ts`): the register's "ไม่เคลื่อนไหว 180 วัน" filter and the audit round's stale_movement preset leave them out. A typed tag that loses the race on the unique index answers `fieldErrors.assetTag: "duplicate"`, as on create. Installed components follow the parent's room, holder and department through the existing sync.
- A tag change (P2-R6): the tag is read-only on the edit page; "เปลี่ยนรหัส" opens a dialog that warns that the printed labels keep the old code and a search by the old code finds nothing (the QR still opens the asset, it encodes the id), takes "รหัสใหม่" and sets the form's tag. The one save writes it with an `asset_tag_change` row ("เปลี่ยนรหัสทรัพย์สิน", the plain old and new codes). No reason is asked. Reprint the label afterwards.
- An open handover (P2-R3, decision 10): while an HO- is open the holder, the room and แผนก are read-only on the edit page, with "ใบส่งมอบ <HO-…> ยังเปิดอยู่ …" and "เปิดใบส่งมอบ" to the document. To correct them, cancel the handover there and hand over again, or return the asset; โอนย้าย refuses an asset with an open handover. The server keeps its 409 `ASSET_CUSTODY_LOCKED_BY_CHECKOUT` and compares the department it computes. The automatic department fix is skipped while the handover is open, so an unrelated edit (a Serial, say) is never refused; แผนก then shows "แผนกไม่ตรงกับผู้ถือครอง จะปรับเมื่อรับคืนหรือโอนย้าย".
- The create form (page group 4 plan 2, spec §8): the card "ข้อมูลที่ต้องกรอก" with "กรอกแล้ว n จาก m ช่องที่ต้องกรอก" holds every required field; the optional sections are folded, each with its summary. The footer names the empty required fields ("ยังขาด n ช่องที่ต้องกรอก · …") with "ไปช่องแรกที่ยังขาด"; บันทึก stays enabled and answers with the errors under the fields. On the desktop the ownership type is five buttons, on the phone a select. "ใช้ที่ตั้งประจำ" copies the home room into ที่ตั้งปัจจุบัน. A photo chosen in รูปแรกเข้าทรัพย์สิน is added at once. `POST /api/assets` writes the asset, its first movement and its audit entry in one transaction, gives a held บุคคล or Stock asset its holder's department, refuses a holder who is no longer active under the field, and answers a typed tag that another save took first with the duplicate error under รหัสทรัพย์สิน (a generated tag is generated again).
- เอกสารจัดซื้อ on the asset form (page group 4 plan 3, spec §8-§9, rulings P3-R1..R9). The section starts open on create and folded on edit, where its summary names the linked documents ("ใบ PO PO-… · ใบกำกับ INV-…", the first 3, then +n) with the badge "ผูกไว้ n ใบ" (create: "เลือกแล้ว n ใบ", plus "รอบันทึก n ใบ" for new uploads). It has two parts, side by side from 1024 px and stacked below it with the upload second:
  - **เลือกเอกสารที่มีอยู่**: a search over the active documents. With no text the list shows the 10 newest (the form's supplier's first), rendered by the page, so opening the form asks nothing (P3-R4); typing 2 characters asks `GET /api/purchase-documents/search` after 300 ms. Each word must match the document number, the PO or invoice number, the supplier's code or name, or a linked active asset's tag, name or **model name**, so "<รุ่น> <รหัสเครื่อง>" finds the PO of a machine already registered. A row reads type · number, supplier name · date · amount, and "ผูกกับ n เครื่อง: <the first 3 names>"; the footer "พบ n ใบ จากเอกสารกลาง N ใบ". A chosen document becomes a chip; a document no longer active stays a chip marked "ปิดใช้งาน", counts in the badge, and can be removed, but the search never offers it (P3-R7).
  - **อัปโหลดเอกสารใหม่**: the file, type, number, date, amount (บาท) and supplier (the asset's unless another is picked); "+ เพิ่มอีกใบ" queues it and opens a new draft. The file stays optional; a number without a file is not uploaded.
  - **The save**: บันทึก first asks `POST /api/purchase-documents/check-duplicates` for every new upload. A type and number already stored (active or not) or twice in this save is refused under the number (or on its queued row) before the asset is saved; nothing is posted and the file and fields stay (P3-R3). Then the asset saves, each new document is created and linked in one multipart request, the newly chosen ones are linked in one JSON request, and on edit each removed chip is unlinked.
  - **Edit**: linking and unlinking happen at บันทึกการแก้ไข, not on click (P3-R5). A chip's × ("เอา <เลขที่> ออก") marks it "จะเอาออกเมื่อบันทึก" with "เก็บไว้" to undo; the change list reads "เอกสารจัดซื้อ: เพิ่ม <เลขที่>" / "เอา <เลขที่> ออก"; ยกเลิก leaves every link as it was. An unlink removes the link only; the document and its files stay.
  - **A failed document step** after the asset is saved goes to `/<locale>/assets/<id>/edit?documents=failed#documents` with เอกสารจัดซื้อ open and a warning that names each failed upload (type, number, file name), handed over in the browser's sessionStorage; the files themselves are not carried over and must be chosen again. Without sessionStorage, or when only a link failed, the warning is a general sentence (P3-R6).
  - **Batch** (spec §8, P3-R8): one search and **one** upload for the whole batch, no "+ เพิ่มอีกใบ". The upload is pre-checked at ยืนยันและบันทึกทั้งชุด; the batch POST then becomes multipart (`payload`, `newDocument`, `file`) and the document is created and linked to every asset inside the batch's transaction. A second file part is refused.
  - **Permissions** (P3-R2): the search and the pre-check need `asset:create` or `asset:edit`; creating, linking and unlinking need `asset:edit`. A user with `asset:create` only sees "ผูกหรืออัปโหลดเอกสารจัดซื้อได้เมื่อมีสิทธิ์แก้ไขทรัพย์สิน" in place of both parts, and the save sends no document step.
- Opening asset detail, edit, or clone from the register preserves the current register URL through a sanitized `returnTo` value. Back, cancel, and save actions return to the same page, filters, sort, and search state instead of resetting the operator to the first page.
- Company and branch on the asset form are the asset owner/tag scope; they drive generated asset tags and reporting/accounting scope.
- Single asset create/edit forms keep Save and Cancel in a fixed bottom action bar so operators do not need to scroll to the end of the long registration form before saving. The existing duplicate, protected-status, and saving guards still control whether Save is enabled.
- Custodian defaults to the selected owner company/branch scope (the single form dropped the department filter in page group 4 plan 2: with the department following the holder it would be circular), but the form can opt in to cross-company custodians for cases where the asset owner and current holder are different organizations.
- When editing an existing asset, a saved custodian outside the owner company/branch scope automatically opens the cross-company custodian mode so the current holder remains visible and can be reviewed before saving.
- Cross-company custodian selections show an explicit warning and are recorded in the creation audit trail. Batch create follows the same model for shared owner/tag scope plus common or row-level custodian values.
- Home/current location defaults to the selected owner branch, but single and batch create can opt in to cross-branch locations when the physical site differs from the branch used for Asset Tag ownership. Cross-branch mode warns the operator and appends each location's branch label in the dropdown to avoid ambiguous repeated location codes.
- Use the Asset Register cross-scope quick filters when reviewing assets that are held or physically located outside their owner/tag scope. The filters separate all cross-scope cases, custodian different company, custodian different branch, and current location different branch while preserving the normal search/company/branch/category context.
- The Dashboard highlights active cross-scope assets as a high-level KPI and review panel. Use those cards as the daily entry point for ownership/custody scope cleanup; they drill into the same Asset Register cross-scope filters and do not change custody, transfer, or master-edit rules.
- Clone sessions show a warning banner reminding users to review custodian, location, purchasing data, and linked documents before saving. Batch mode is hidden during a clone session so the prefilled single-asset draft is not lost by switching modes.

## Asset Scan And Labels

- Print Asset Label QR codes from the label workflows, using the configured Public QR Base URL when printing for production.
- Prepare labels on `/asset-management/labels` (`asset:view`; page group 4 plan 6, spec §11, board AR-Labels). From `xl` it has two columns: the search and the label queue (คิวป้าย) on the left, the print list (รายการที่จะพิมพ์) and the settings and preview card (ตั้งค่าและตัวอย่าง) on the right; one column below.
- The register's "พิมพ์ป้าย N รายการ" opens this page in the same tab with `?assetIds=<id,id,…>&from=register` (P6-R1), no longer the print route. The page keeps the register's order, drops repeats and looks up the first 100 ids; ids past 100 are refused in the list's status line ("เพิ่มได้ a จาก b รายการ เพราะรายการพิมพ์รับได้สูงสุด 100 ดวง"). The line "<n> รายการนี้มาจากที่เลือกในทะเบียนทรัพย์สิน" shows only with `from=register`, counts the register's rows still listed and goes with the last of them or with "ล้างรายการพิมพ์".
- The search ("รหัสทรัพย์สิน ชื่อ Serial ผู้ถือครอง หรือที่ตั้ง", 2 or more characters, assets only) finds the ids, then asks the queue's lookup (`GET /api/assets/label-prints?ids=`) for their rows, so every result shows its real print state. A tap adds the result to the print list.
- The queue has four modes: ยังไม่เคยพิมพ์ · เคยพิมพ์แล้ว · ทั้งหมดล่าสุด · ต้องพิมพ์ใหม่ (`Segmented` from `md`, a select below), and six filter chips: บริษัท, สาขา, ที่ตั้ง (a search box over the rooms), หมวดหมู่, สร้างเมื่อ (a date range) and เรียงคิว. Options read "code - name"; a closed chip reads "<filter>: <name>". "ล้างตัวกรอง" clears the chips and the order and keeps the mode.
- A queue row is one button: the name first, then "<tag> · <holder, or ส่วนกลาง> · <room>", then its state: ยังไม่เคยพิมพ์, เคยพิมพ์แล้ว, อยู่ในรายการพิมพ์ (already listed; pressing it does nothing) or "ป้ายเดิม <tag>" whenever the tag on the last printed label differs from today's. - On mobile, the Asset Label scanner uses an undistorted 4:3 camera preview with a smaller square QR guidance frame. It defaults to the generic environment-facing rear camera when multiple devices are reported, requests high-resolution 4096x3072/30fps ideal constraints with continuous focus/exposure where supported, and best-effort applies the camera track's maximum reported resolution after the stream opens. Supported QR camera tracks expose bounded 1x/2x/3x zoom controls to scanner surfaces so users can hold the label slightly farther away while keeping the QR large, then return to the unzoomed 1x preview without restarting the camera; unsupported devices hide those controls. Asset QR decoding uses a shared direct `getUserMedia` stream plus ZXing `BrowserQRCodeReader.decode(video)` so it reads the native-resolution video frame rather than the CSS-pixel hidden canvas used by `html5-qrcode`; this avoids mobile native detector gaps and mirror-flip retries. Users should center only the QR code in the frame and adjust distance until the QR modules are sharp. Reusable Serial Number scanner inputs use the same native-resolution camera path with ZXing `BrowserMultiFormatReader`, optional browser `BarcodeDetector`, focused scan-band crops that decode crop `ImageData` directly through ZXing `RGBLuminanceSource`/`BinaryBitmap` before full-frame fallback, QR plus common 1D/2D barcode formats, a 16:9 preview, and a narrow barcode guide with scan line for manufacturer labels; users should center the barcode band on the line, make the bars fill most of the frame, and keep the barcode lines sharp.

## Asset Custody

- Check-out records who receives the asset and captures handover evidence.
- The ส่งมอบ page (group 3 plan 1) has three sections (ทรัพย์สินที่จะส่งมอบ, ส่งมอบให้ใคร, หลักฐาน) beside the "สรุปก่อนบันทึก" card (now / after the save for holder, department, location, status and components, with a checklist); "ตรวจสอบและบันทึก" opens the review "ตรวจสอบก่อนส่งมอบ", and ยกเลิก goes back to `returnTo` or the register. The destination is พนักงาน / แผนก / ที่ตั้ง; the department follows the department rule (`src/lib/asset-department-rule.ts`: a บุคคล or Stock asset takes the receiver's, a ส่วนกลาง asset keeps its own), and the installed components go along and are listed. On the phone the same form is three steps: the asset and receiver ("ถัดไป: ให้ผู้รับตรวจ"), the receiver reads it back ("ถูกต้อง ลงชื่อรับ"; this step replaces the review dialog), then the receiver signs and "บันทึกการส่งมอบ" saves and opens the HO-.
- ส่งมอบ and condition (group 3 spec §19, 2026-10-31): สภาพก่อนส่งมอบ offers only ใหม่, ดี and พอใช้, and an asset recorded ยังไม่ประเมิน starts with none chosen. An asset recorded เสียหาย or ใช้งานไม่ได้ is still found but refused ("สภาพเสียหาย ต้องส่งซ่อมก่อนส่งมอบ" / "ใช้งานไม่ได้ ต้องส่งซ่อมก่อนส่งมอบ"); IT can pick it to read the reason under the field, with a **ส่งซ่อม** link that opens a new repair for it (`/maintenance/new?assetId=`). A ซาก asset reads "เป็นซาก รอตัดจำหน่าย ส่งมอบไม่ได้" with no link. The route refuses the same (409 `ASSET_CHECKOUT_CONDITION_BLOCKED`). The ส่งซ่อม link shows only to someone who may record a repair (`maintenance:create`). Once the repair closes as ใช้งานได้ with ดี or พอใช้, the asset can be handed over at once. The condition chosen at the handover is written to the asset when it differs (so a ยังไม่ประเมิน asset handed over as ดี becomes ดี), and the asset's history shows "เปลี่ยนสภาพ … → …" with the HO- number. The asset's register photo (the model's photo first, else the asset's newest image) shows in the search rows, beside the chosen asset, in the "สรุปก่อนบันทึก" card and on the phone's step 2; รูปก่อนส่งมอบ shows a small preview once chosen; an asset without a photo shows the empty frame.

A computer with components lists them under "ส่วนควบที่ต้องได้คืน", all ticked; one unticked reads ยังไม่ได้คืน and stays with ผู้คืน. ผู้คืน starts as the holder and ผู้รับคืน as you ("คุณ"); the condition chips have no default; the return date is no later than today and no earlier than the handover. "หลังรับคืนให้เป็น" offers พร้อมใช้งาน / ส่งซ่อม / รอตัดจำหน่าย (ส่งซ่อม only to someone with `maintenance:create`, or on a row with an open repair), and "เก็บไว้ที่" is searchable with no default. A เสียหาย or ใช้งานไม่ได้ condition picks ส่งซ่อม, and ซาก picks รอตัดจำหน่าย. Photos are typed ภาพรวม or จุดเสียหาย. "ตรวจสอบและบันทึก" opens "ตรวจสอบก่อนรับคืน", which saves and opens the RT-. On the phone the same parts are condensed: one "ผู้คืน / ผู้รับคืน: … · แก้ไข" line, the camera for photos, and the footer's "ส่วนควบได้คืน N · ขาด M". - The โอนย้าย page (group 3 plan 3) has three sections (ทรัพย์สิน, เปลี่ยนอะไร, เหตุผล) beside the "สรุปก่อนบันทึก" card. The footer reads "โอนย้าย <tag>: …"; "ตรวจสอบและบันทึก" reads the asset again, then opens "ตรวจสอบก่อนโอนย้าย" (real changes only), which saves and opens the TR-. On the phone the rows stack with "ตอนนี้: …" above each picker, the chip reads ปรับโครงสร้าง, and the footer carries the "เปลี่ยน N อย่าง" line.
- The ย้ายที่ตั้งหลายรายการ page (group 3 plan 4) works on the desktop only. Above the table, a search region filters by words (at most 5, each matching one field), ที่ตั้งตอนนี้ (an exact active room) and หมวดหมู่, and reads "พบ N รายการ"; the first page comes from the server, and every later page, filter or refresh is fetched from `GET /api/asset-operations/bulk-move-list` (`asset:edit`, 25 rows a page, by tag). On the phone the page shows only the notice "หน้านี้ใช้บนคอมพิวเตอร์" and a link to the register.
- Check-in records return and receiving parties and can route the asset to Ready, "ส่งซ่อม" (`Under Maintenance` plus an unfinished repair record created in the same transaction, or the open one joined; the RT- links it), or Pending Disposal.
- Users with `asset:edit` can cancel the latest Check-out, Check-in, or Transfer from Asset Detail's **อื่น ๆ** menu (on the phone, **การดำเนินการอื่น** in the bottom bar) or from the operation document. The dialog previews the current state, state to restore, original operator, and affected components; a reason of at least 5 characters is mandatory.
- Automatic cancellation is allowed only when the document is active, is the latest transaction for that asset, its snapshot still matches the current asset/components, and no downstream workflow depends on it. A successful cancellation keeps the original document as `VOID`, writes a compensating movement and System Log, and restores the complete captured snapshot rather than guessing a status.
- If automatic cancellation is unsafe, the system does not partially restore data. It creates/updates a pending `transaction_cancellation_blocked` item in **Admin > Data Quality** for review. Historical documents created before snapshot support are intentionally not auto-cancellable.
- Cancelling a Check-in reopens its related Check-out. The database permits only one active Check-in per Check-out; VOID Check-ins stay available as evidence and do not prevent a later corrected Check-in. It also puts every component the return left out back as installed with its earlier reference, unless one has already come back late.
- Check-out, Check-in and Transfer pick their assets in one shared picker (`AssetOperationPicker`) on one server search (`GET /api/asset-operations/search`, `asset:edit`): type 2 or more characters, at most 20 rows with the true count, an exact code first. The text splits on spaces into at most 5 words, each of which must match one field (the asset's and the holder's department names included), while the exact and prefix code tiers use the whole text. It follows the Asset Detail page's rules; an asset the transaction cannot take is still listed, faint, with its reason, and the save routes refuse the same assets (409, spec 6.5 of `docs/superpowers/specs/2026-10-28-server-asset-search-design.md`). On Transfer, a บุคคล asset outside `Ready`/`In Use` can be moved to another location or department with no custodian chosen, but not given a custodian; Asset Detail's โอนย้าย reads the custodian rule and stays disabled for it. A broken asset (เสียหาย, ใช้งานไม่ได้, ซาก) is the same since group 3 plan 3: it moves with no holder chosen, is cleared with "นำ … ออกแล้ว: <reason>" when one is, and Asset Detail's โอนย้าย is disabled for a broken บุคคล asset (P3-R1).
- Check-in has one asset field. It finds by Asset Tag, serial number, fixed-asset code, the holder's code or name, the HO- number, or the current location's code or name, and groups the rows by holder. Held rows (an open handover or a custodian) come right after an exact code, before the code-prefix and other matches. Return-by starts as the row's holder, even one who is no longer an active employee: the select then offers that person once more as "{code - name} (พ้นสภาพ)", and the RT- records them. Legacy/imported assets in `Ready` or `In Use` that already have a current custodian but no active checkout show as ข้อมูลเก่า rows: picking one asks once ("สร้างใบส่งมอบย้อนหลังแล้วรับคืน"), then creates the backfilled handover (`legacy_return_backfill`, unchanged) and continues the normal return form; their second line names the room they are in. A handover with an unfinished repair record comes back into ส่งซ่อม under that repair; a ข้อมูลเก่า row with one, ส่วนควบ (they come back with their parent) and License assets are listed with their reason and cannot be picked. A repair record saved by mistake can be cancelled ("ยกเลิกบันทึก") while it is unfinished; cancellation restores the custody-derived status (`In Use` with an active checkout or personal custodian, otherwise `Ready`). The backfill creates `AssetCheckout`, `AssetMovement`, and `SystemLog` records with `legacy_return_backfill` so the return stays auditable instead of bypassing the check-in workflow. The rows carry a badge (the HO- number, ข้อมูลเก่า ไม่มีใบส่งมอบ, or ส่วนควบค้างคืน). A component left out of an earlier return has its own row, "ส่วนควบค้างคืน ของ <parent tag> · RT-…", found by its tag, its name or its holder, under the holder's group, and never a ข้อมูลเก่า row. Picking it opens the late-return panel in place of sections 2 and 3: the parent and the RT-, ผู้รับคืน, the date, an optional condition and a remark. When the parent is in IT stock (active, พร้อมใช้งาน, no holder, no open handover, no open repair) the component is re-attached to it and takes its room and department; otherwise it stands alone in the room the panel asks for, with the return department (a ส่วนกลาง one keeps its own). Either way its holder is cleared, and the RT- gains the line "<tag> คืนแล้ว <date> · รับโดย <name>". `?assetId=` of an outstanding component starts on its row. ส่งมอบ of a parent with an outstanding component warns "ยังค้างคืน N รายการ: …" in section 1 (the phone's step 1).
- Transfer records location/custodian/department movement. Choosing a destination custodian other than the current one sets the asset status to `In Use` in the API transaction; location-only or department-only transfers keep the current status. The department follows the transfer rule (`getTransferNextDepartmentId`): a บุคคล or Stock asset takes the new holder's department, or the current holder's when no new one is chosen; ส่วนกลาง and ส่วนควบ keep a free department. A change has its own เปลี่ยนแผนก history line beside the transfer's. The TR- prints แผนกเดิม and แผนก. A transfer to a holder still creates no handover, so the asset later returns through รับคืน's ข้อมูลเก่า row (P3-R22). ## Maintenance And PM

Since 2026-10-07 (branch `feat/simple-repair-records`) maintenance is a one-form repair log. Staff guide: `docs/17_REPAIR_RECORD_GUIDE_TH.md`. Design: `docs/superpowers/specs/2026-10-07-simple-repair-records-design.md`.

- A repair record (`maintenance_tickets` row) has three statuses: `in_progress` (not finished yet: sent out or waiting for parts), `closed` (finished, with an `outcome`), and `cancelled` (recorded by mistake; kept as history). Old rows with `open`, `reported`, `accepted`, `waiting_parts`, `waiting_vendor`, or `completed` count as `in_progress` everywhere and are never written again. `openRepairRecordWhere` in `src/lib/repair-record-policy.ts` is the single filter for unfinished records.
- `outcome` (new nullable column) is `usable` (default) or `beyond_repair`; `NULL` on old closed rows displays as "ไม่ระบุ".
- Record a repair from Asset Detail ("บันทึกซ่อม", also reached by scanning the asset QR) or from `/maintenance/new`. The form asks for asset, date (defaults to today in Thai time), "อาการ / สิ่งที่ซ่อม", finished or not, and the outcome when finished. A collapsed "รายละเอียดเพิ่มเติม" holds vendor (blank = internal repair), total cost, invoice number, photos/receipts, and remark. The recorder is the employee linked to the signed-in account; an account with no employee link must choose one.

- System Settings includes a key/description/section finder and changed-setting links that return the operator to the relevant existing settings tab. The unsaved-change review and save semantics remain unchanged. Empty, error, and access-denied surfaces reuse `ActionEmptyState` so state messaging and action spacing stay consistent across the dashboard.

## Permanent assignment and temporary loan

1. On Asset Handover, choose the destination. A user destination must explicitly choose `มอบหมายใช้งานประจำ` or `เบิกใช้งานชั่วคราว`; non-user destinations are temporary loans.
2. Permanent assignment requires an employee custodian, hides the due date, and saves the asset as `In Use`.
3. Temporary loan requires a due date on/after the handover date and saves the asset as `Checked Out`.
4. Asset Return shows read-only current-custody context (`ใช้งานประจำ` / `เบิกชั่วคราว`) and validates mode plus current status before any write.
5. Return completes to the existing allowed statuses (`Ready`, `Under Maintenance` via "ส่งซ่อม", or `Pending Disposal`). Cancelling a return restores the mode-authoritative before snapshot; cancelling a handover restores its original snapshot.
6. Do not manually change the lifecycle status while an active handover exists. Use Return, transaction cancellation, or Asset State Review.

The same return outcomes apply to both custody modes. The difference is the authoritative source status before return: permanent assignment returns from `In Use`, while temporary loan returns from `Checked Out`.
